Arsitektur Infrastruktur Kmtxpumit

Dokumen ini menjelaskan bagaimana platform swt-kmtxpumit-platform-fs berjalan: dari kode yang ditulis developer, menjadi image di registry, sampai menjadi pod yang melayani pengguna di atas cluster Kubernetes dua node milik sendiri, termasuk siapa yang boleh mengaksesnya dan apa saja batas yang sudah diketahui.

00Ringkasan

Lima kalimat yang menjelaskan seluruh sistem. Sisanya hanya memperdalam bagian ini.

Analogi singkat

Bayangkan dua gudang sewaan yang berdiri terpisah di kota yang sama. Gudang pertama hanya berisi kantor mandor yang mengatur pekerjaan, gudang kedua yang benar-benar berisi mesin dan barang. Karena keduanya tidak punya jalan pribadi, dibuatlah terowongan tertutup antar keduanya, yaitu WireGuard. Traefik adalah satpam di pintu depan gudang kedua, dan setiap ruangan di dalamnya dipisah menjadi dua kamar terkunci: satu untuk uji coba, satu untuk pengguna sungguhan.

  1. Developer mendorong kode ke branch development atau production di GitHub. Tidak ada berkas aplikasi yang diunggah manual ke server.
  2. GitHub Actions menguji lalu membangun lima image dan mengirimkannya ke GHCR, dengan tag mengikuti nama branch.
  3. Operator menjalankan kubectl apply sendiri di node master. Tahap ini sengaja tidak diotomatiskan, karena otomasi berarti menyerahkan kunci cluster ke pihak ketiga.
  4. Kubelet di node worker menarik image dari GHCR dan menjalankannya sebagai pod. Semua beban kerja berada di satu node worker.
  5. Pengguna masuk lewat Traefik yang mendengarkan langsung di port 80 dan 443 milik node worker, lalu diarahkan ke layanan sesuai nama domain.

Dua node, satu yang bekerja

Node k8s-master hanya menjalankan control plane. Seluruh pod aplikasi, database, dan Traefik dijadwalkan di k8s-worker.

Dua environment, satu cluster

Namespace kmtxpumit-development sudah hidup dan terpakai. Namespace kmtxpumit-production sudah ada di manifest, tetapi belum pernah dijalankan.

Tanpa High Availability

Hanya ada satu control-plane node. Jika node master mati, seluruh cluster berhenti. Ini keputusan sadar, bukan kelalaian.

01Lapisan platform

Di mana sebenarnya semua ini berjalan.

Bahasa sederhana

Tidak ada layanan cloud terkelola di sini. Yang disewa hanya dua mesin virtual kosong dari Hostinger. Di atas keduanya dipasang sendiri sistem operasi, mesin container, lalu Kubernetes, sehingga lapisannya menjadi empat: VPS, Ubuntu, containerd, lalu pod.

Control plane tunggal

Cluster dinyalakan dengan kubeadm init memakai alamat tunnel, bukan IP publik. Parameter --control-plane-endpoint disiapkan sejak awal agar penambahan node control-plane ketiga nanti tidak perlu membangun ulang cluster dari nol.

Beban kerja terpusat

Node master tidak menjalankan pod aplikasi. Akibatnya seluruh kapasitas aplikasi ditanggung satu node worker dengan 2 vCPU dan 7.8 GiB memori.

Konsekuensi yang diterima

Tanpa node kedua untuk control plane, etcd, API server, dan scheduler adalah titik gagal tunggal. Penambahan node ketiga untuk quorum baru direncanakan, belum dikerjakan.

02Jaringan cluster

Bagaimana dua mesin yang hanya punya IP publik bisa menjadi satu cluster yang aman.

Bahasa sederhana

Provider tidak menyediakan jaringan privat antar VPS, sehingga kalau dibiarkan apa adanya, seluruh percakapan internal cluster akan melewati internet terbuka. Solusinya dua lapis: sebuah terowongan terenkripsi antar node untuk lalu lintas Kubernetes, dan sebuah jaringan internal khusus pod agar setiap pod punya alamat sendiri dan bisa saling dihubungi.

Lapisan pertama — tunnel WireGuard

Seluruh komunikasi antar node, yaitu API server, etcd, kubelet, dan jaringan pod, dilewatkan tunnel WireGuard. IP publik hanya dipakai untuk SSH dan untuk endpoint WireGuard itu sendiri. Cluster dibangun di atas alamat tunnel, bukan alamat publik, sehingga API server tidak pernah terekspos langsung ke internet.

Lapisan kedua — CNI Calico

Calico dipilih di atas Flannel karena mendukung NetworkPolicy standar Kubernetes, yaitu kemampuan membatasi pod mana boleh menghubungi pod mana. Tanpa itu, klaim bahwa cluster ini layak produksi tidak punya dasar.

Dipasang lewat Tigera Operator. CIDR pod 192.168.0.0/16, sama dengan nilai yang diberikan ke kubeadm init.

Enkapsulasi VXLAN

Bukan IPIP bawaan. VXLAN dipilih karena lebih kompatibel di lingkungan VPS yang kadang memblokir protokol IPIP.

calico-apiserver dilewati

Sengaja tidak dipasang. Akibatnya GlobalNetworkPolicy dan Tier tidak tersedia, hanya NetworkPolicy standar, dan itu memang cukup untuk skala dua node.

Sudah dibuktikan, bukan diasumsikan: sebuah pod uji berhasil menghubungi pod nginx sebelum policy dipasang, lalu gagal dengan timeout setelah NetworkPolicy yang membatasi ingress diterapkan. Artinya Calico benar-benar menegakkan aturan, bukan sekadar menerimanya.

03Dari kode ke image

Bagian yang berjalan otomatis, sepenuhnya di luar cluster.

Bahasa sederhana

Node Kubernetes tidak bisa membangun aplikasi dari kode sumber. Ia hanya bisa menarik paket siap jalan dari sebuah gudang. Maka setiap kali kode didorong ke GitHub, GitHub sendiri yang menguji, mengemas, lalu menaruh hasilnya di gudang bernama GHCR.

  1. Developer mendorong ke development atau production. Branch master sudah tidak ada, hasil rename pada 2 September 2026, dan production kini menjadi branch default.
  2. Dua pekerjaan berjalan paralel. Job web menjalankan typecheck, build, dan test untuk tiga aplikasi Svelte beserta paket bersama. Job backend menjalankan build, vet, dan test Go dengan Postgres sungguhan sebagai layanan CI, termasuk menjalankan berkas migrasi.
  3. Job images menunggu keduanya hijau, lalu menjalankan lima docker build terpisah.
  4. Lima image dikirim ke GHCR memakai token bawaan GitHub, tanpa perlu token pribadi.

Penamaan tag

  • Push ke development menghasilkan tag development yang dipakai overlay, ditambah development-<sha-pendek> untuk menelusuri commit persisnya.
  • Push ke production menghasilkan tag production dan production-<sha-pendek>.
  • Tidak ada lagi tag latest polos, supaya kedua environment tidak pernah berebut satu tag yang sama.

Yang pernah salah dan sudah diperbaiki: setelah branch master di-rename, berkas CI masih mencocokkan refs/heads/master. Selama beberapa hari, push ke production tidak membangun image sama sekali, sementara statusnya tetap hijau karena langkah build hanya dilewati, bukan gagal.

Alamat API ikut dipanggang ke dalam bundle

Ketiga aplikasi web adalah SPA statis. Nilai VITE_API_BASE dibaca saat build, bukan saat pod berjalan, lalu ikut tertanam di bundle JavaScript. Akibatnya alamat API yang salah tidak bisa diperbaiki lewat variabel lingkungan di Kubernetes, melainkan harus dibangun ulang image-nya.

docker build -f deploy/marketplace.Dockerfile \ --build-arg VITE_API_BASE=https://development-api.kmtxpumit.my.id \ -t ghcr.io/pt-sagung-wahana-teknologi/kmtxpumit-marketplace:development .

04Dari image ke cluster

Bagian yang sengaja tetap manual, dan alasannya.

Bahasa sederhana

Setelah image siap di gudang, tidak ada yang otomatis memasangnya. Operator masuk ke node master, membaca dulu apa yang akan dipasang, baru menjalankan satu perintah pemasangan. Jeda itu disengaja, karena memberi otomasi akses pasang berarti menyerahkan kunci cluster.

Kustomize, bukan Helm, untuk aplikasi

Manifest aplikasi ditulis sebagai kustomize: satu folder base berisi definisi yang sama untuk semua environment, dan satu folder overlays per environment yang hanya menimpa hal yang memang berbeda, yaitu nama namespace, tag image, nama domain, daftar origin CORS, dan konfigurasi. Helm tetap dipakai, tetapi hanya untuk memasang Traefik.

  • Membaca dulu dengan kubectl kustomize overlays/<env>, lalu kubectl apply --dry-run=server yang memvalidasi manifest terhadap cluster tanpa memasang apa pun.
  • Memasang dengan kubectl apply -k overlays/<env>, menghasilkan sekitar dua belas resource.
  • Memperbarui versi dengan kubectl rollout restart, karena tag image stabil sehingga pod yang sudah berjalan tidak menarik ulang image hanya karena isi tag berubah di registry.

Konsekuensi tag stabil: kubectl apply -k saja tidak cukup setelah CI membangun image baru. Tanpa rollout restart, pod lama tetap menjalankan image lama meski isi tag di registry sudah berganti.

Mengapa pemasangan tidak diotomatiskan

Membangun dan mengirim image hanya butuh izin menulis ke registry. Kalau token itu bocor, kerusakan terbesarnya adalah image di registry tertimpa. Menjalankan kubectl apply dari GitHub Actions berbeda kelas: ia menuntut berkas admin.conf disimpan sebagai rahasia repo, dan berkas itu memberi akses cluster-admin penuh ke seluruh cluster, bukan hanya ke satu environment.

05Jalur traffic saat aplikasi dipakai

Apa yang terjadi antara pengguna mengetik alamat dan data muncul di layar.

Bahasa sederhana

Semua kunjungan berhenti dulu di satu satpam bernama Traefik, yang berdiri di node worker dan mendengarkan langsung di port 80 dan 443 milik mesin itu. Satpam membaca nama domain yang diketik pengunjung, lalu mengantar ke ruangan yang benar. Halaman web dan permintaan data memakai domain berbeda, sehingga keduanya diantar ke tujuan berbeda pula.

Kenapa Traefik tidak memakai LoadBalancer

Chart bawaan Traefik membuat Service bertipe LoadBalancer, dan tipe itu hanya mendapat alamat bila cluster berjalan di penyedia cloud yang punya controller untuk itu. Di VPS polos, kolom EXTERNAL-IP akan berstatus pending selamanya. Karena itu dipakai hostPort: pod Traefik mendengarkan langsung di port 80 dan 443 milik node, melewati Service yang tidak pernah terisi. Status pending pada Service itu normal dan bukan tanda kesalahan.

DomainDiantar keCatatan

development-api.kmtxpumit.my.idService apiDipanggil peramban setelah halaman termuat.

DNS harus mengarah ke worker: seluruh record perlu menunjuk IP publik k8s-worker, bukan master, karena semua pod termasuk Traefik dijadwalkan di sana. Salah arah membuat koneksi habis waktu tanpa pesan yang jelas.

Berkas yang mengatur perutean

  • base/ingressroute.yaml — rute api sekaligus pemblokiran /internal/api/v1.
  • base/marketplace-ingressroute.yaml, ops-ingressroute.yaml, vendor-ingressroute.yaml — rute tiap aplikasi web.
  • base/middleware-cors.yaml — daftar origin, berisi nilai sementara yang selalu ditimpa overlay.
  • base/serverstransport.yaml — pengaturan koneksi Traefik ke layanan di belakangnya.

Nama entrypoint websecure dan resolver sertifikat le sengaja disamakan persis dengan yang dipakai di berkas compose lama, supaya manifest tetap nyambung saat berpindah dari satu VPS ke cluster.

Catatan hardening yang belum selesai: Traefik sendiri memperingatkan bahwa izin berkas acme.json, tempat sertifikat disimpan, bisa berubah setiap Traefik dimulai ulang, karena volume penyimpanannya dipasang tanpa langkah pembetul izin.

06Rahasia & registry

Dua brankas dengan kegunaan yang sama sekali berbeda.

Bahasa sederhana

Brankas pertama dipakai aplikasi untuk membaca password database. Brankas kedua dipakai node untuk membuktikan dirinya berhak menarik image dari gudang yang sengaja ditutup untuk umum. Keduanya tidak pernah ikut masuk ke repositori kode.

kmtxpumit-secrets

Dibuat langsung lewat perintah di node master, bukan dari berkas yang di-commit. Berisi lima kunci: pengguna, password, dan nama database, satu token layanan, serta alamat koneksi database yang sudah lengkap.

ghcr-pull

Kredensial registry bertipe docker-registry. Memakai token dengan izin baca paket saja, bukan token tulis milik CI. Tanpa ini, pod berhenti di ImagePullBackOff dengan pesan tidak sah.

Keduanya per namespace

Secret tidak merambat antar namespace meski namanya sama. Keduanya wajib dibuat ulang di namespace production, dengan password database yang berbeda dari development.

Password dibuat dalam bentuk heksadesimal, bukan base64. Keluaran base64 bisa mengandung karakter yang punya arti khusus di dalam URL, dan alamat koneksi database adalah sebuah URL. Gejalanya menyesatkan: api dan worker gagal berulang dengan pesan soal port yang tidak sah, seolah masalah jaringan, padahal penyebabnya bentuk password.

Registry sengaja tetap privat

Paket baru di GHCR bersifat privat secara bawaan, dan itu dipertahankan karena repositori kodenya juga privat. Konsekuensinya harus diterima secara sadar: node tidak bisa menarik image sebelum kredensial registry dibuat di namespace yang bersangkutan.

Dua token berbeda, sengaja tidak dipakai ulang

  • Token tulis hanya dipegang GitHub Actions, itu pun token bawaan yang dibuat otomatis per jalannya workflow.
  • Token baca dipegang cluster, hanya untuk menarik image. Token ini boleh dipakai di kedua namespace karena sifatnya hanya membaca.

ConfigMap

Nilai yang tidak rahasia berada di base/configmap.yaml dan ditimpa per environment. Satu nilai masih menunggu keputusan: awalan nomor faktur di overlay production masih berupa penanda sementara. Nilai itu perlu diisi sebelum faktur produksi pertama terbit, karena penomoran tidak bisa diubah di tengah jalan.

07Data & penyimpanan

Di mana data disimpan, dan bagian mana yang masih dikerjakan tangan.

Bahasa sederhana

Pod bersifat sementara. Kalau database dijalankan begitu saja, datanya hilang setiap pod dimulai ulang. Karena itu dipasang penyedia penyimpanan yang menyediakan ruang tetap di cakram node worker, lalu database dan berkas unggahan dipasangkan ke ruang itu.

StorageClass local-path

Penyedia volume dari Rancher, dijadikan kelas penyimpanan bawaan. Volumenya berada di cakram node worker itu sendiri, bukan penyimpanan jaringan.

PostgreSQL

Dijalankan sebagai StatefulSet dengan volume tetap sendiri, satu instans per namespace. Data development dan production tidak pernah bercampur.

SeaweedFS

Penyimpanan berkas untuk kebutuhan aplikasi, juga berbentuk StatefulSet dengan volume sendiri.

Volume artefak bersama

Satu volume dipakai bersama oleh api dan worker, tempat menyimpan berkas hasil olahan seperti faktur PDF.

Batas nyata penyimpanan lokal: karena volume menempel pada cakram node worker, data tidak ikut berpindah bila pod dijadwalkan ke node lain. Pada cluster ini hal itu belum menjadi masalah karena memang hanya ada satu node yang menjalankan beban kerja.

Dua langkah yang tidak ikut otomatis

  1. Migrasi skema. Memasang manifest hanya menyalakan container database yang masih kosong. Sebelas berkas migrasi dijalankan sekali per environment lewat koneksi terusan dari node master. Perlu diulang persis bila volume database pernah dihapus.
  2. Pembuatan admin pertama. Migrasi membuat tabel, bukan isinya. Tabel pengguna tetap kosong, dan tidak ada halaman pendaftaran admin di aplikasi mana pun, karena halaman seperti itu berarti siapa saja di internet bisa mengangkat dirinya menjadi admin. Admin pertama dibuat lewat perintah khusus yang menyambung langsung ke database.

Status jujur: perintah pembuatan admin pertama ditulis pada 2 September 2026 dan sudah ditinjau manual, tetapi belum pernah dibuktikan berhasil dikompilasi maupun dijalankan terhadap database sungguhan. Kegagalan di titik ini adalah temuan yang wajar, bukan kesalahan pemakai.

Kebijakan bawaan ditetapkan lebih dulu, SSH diizinkan, aturan Kubernetes ditambahkan, seluruh aturan ditinjau sebelum firewall dinyalakan, lalu hasilnya diverifikasi dari sesi SSH baru, bukan dari sesi lama yang sudah terhubung, sebelum sesi lama ditutup.

09Dua environment

Dua kamar terpisah di dalam satu cluster yang sama.

Bahasa sederhana

Pemisahan antar environment di sini bukan lewat mesin yang berbeda, melainkan lewat namespace. Setiap namespace punya database, rahasia, volume, dan domainnya sendiri. Traefik adalah satu-satunya komponen yang berdiri di luar keduanya dan tahu harus mengantar ke kamar mana.

Risiko yang belum ditangani

Tidak ada ResourceQuota maupun LimitRange per namespace. Di cluster yang hanya punya satu node beban kerja, development bisa menghabiskan sumber daya sampai production kelaparan.

Isolasi yang sudah ada

Rahasia, volume, database, dan domain terpisah penuh. Secret tidak merambat antar namespace meski namanya identik.

Jalur promosi

Tidak ada promosi otomatis dari development ke production. Keduanya dipasang dengan perintah terpisah dan rahasia berbeda, dijalankan sadar oleh operator.

10Peta berkas di repo

Di mana setiap bagian arsitektur ini benar-benar tinggal.

Repositori swt-kmtxpumit-platform-fs berisi satu backend Go, tiga aplikasi Svelte, paket bersama, dan seluruh berkas penyebaran. Bagian yang relevan dengan dokumen ini ada di dua tempat: definisi alur otomatis, dan folder deploy/.

swt-kmtxpumit-platform-fs/ ├── .github/workflows/ci.yml # job web + backend + images ├── apps/ │ ├── backend/ # Go, satu-satunya backend │ │ ├── cmd/api/main.go # dikompilasi jadi image api │ │ ├── cmd/worker/main.go # dikompilasi jadi image worker │ │ ├── cmd/bootstrap-admin # pembuat admin pertama │ │ └── db/migrations/ # sebelas berkas migrasi │ ├── marketplace/ # SvelteKit statis │ ├── ops/ # SvelteKit statis, masih kerangka │ └── vendor/ # SvelteKit statis, sebelas layar ├── packages/ # contracts, ui, ui-tokens └── deploy/ ├── api.Dockerfile ├── worker.Dockerfile ├── marketplace.Dockerfile # ops dan vendor berpola sama ├── docker-compose.yml # target lama, satu VPS tanpa cluster └── k8s/ ├── README.md # dokumentasi versi lengkap ├── base/ # definisi yang sama di semua environment └── overlays/ ├── development/ └── production/

Isi folder base

  • Beban kerja — Deployment dan Service untuk api, marketplace, ops, dan vendor, serta Deployment worker yang sengaja tidak punya Service.
  • Data — StatefulSet dan Service untuk Postgres dan SeaweedFS, ditambah satu klaim volume untuk artefak bersama.
  • Perutean — IngressRoute per aplikasi, middleware CORS, dan pengaturan transport Traefik.
  • Konfigurasi — ConfigMap, serta contoh berkas rahasia yang berfungsi sebagai bacaan dan tidak boleh dipasang apa adanya.
  • Opsional — satu agen bantu yang bukan bagian platform, diakses hanya lewat terusan, dan berjalan dengan hak sangat luas sehingga komentarnya wajib dibaca sebelum dipakai.

Isi folder overlay

Setiap overlay hanya berisi hal yang memang berbeda: nama namespace, tag image, nama domain di tiap IngressRoute, daftar origin CORS, dan penimpaan konfigurasi. Overlay production mengikuti pola yang sama persis, hanya tanpa awalan development- pada domainnya.

11Ringkasan keamanan

Yang sudah terpasang, dan yang masih terbuka.

Sudah terpasang

  • Seluruh lalu lintas internal cluster terenkripsi lewat tunnel, karena provider tidak menyediakan jaringan privat.
  • API server tidak terekspos ke internet. Cluster dibangun di atas alamat tunnel, dan port kontrolnya hanya diizinkan dari subnet tunnel.
  • Dua lapis firewall yang saling melengkapi, satu di panel penyedia dan satu di dalam sistem operasi.
  • NetworkPolicy benar-benar ditegakkan, dibuktikan lewat percobaan sebelum dan sesudah policy dipasang.
  • Berkas kunci cluster dilindungi dengan izin baca-tulis khusus root, dan salinan cadangannya dienkripsi lalu disimpan di luar server, bukan di server.
  • Kunci cluster tidak pernah diserahkan ke pihak ketiga. Otomasi berhenti di registry.
  • Rahasia tidak pernah masuk repositori, dibuat langsung lewat perintah di node master.
  • Permukaan publik ditekan: dashboard Traefik dimatikan, jalur internal diblokir di tingkat perutean, dan pod worker tidak punya Service.

Masih terbuka

SSH terbuka ke internet

Port 22 menerima dari mana saja karena IP pemilik berubah-ubah. Pengerasan lewat pembatasan percobaan masuk dan penonaktifan otentikasi password belum dipasang.

Tidak ada cadangan etcd

Belum ada snapshot terjadwal. Bila node master rusak sekarang, cluster hilang tanpa jalur pemulihan.

Tidak ada pemantauan

Tidak ada pengumpulan metrik, log terpusat, maupun peringatan otomatis. Node atau komponen yang mati tidak akan memberi tahu siapa pun.

Tanpa batas sumber daya

ResourceQuota dan LimitRange per namespace sempat dirancang tetapi belum terbukti terpasang.

Tanpa PodSecurity

Aturan penerimaan pod belum diatur, sehingga container masih bisa berjalan sebagai root atau dengan hak istimewa tanpa dicegah.

Tanpa RBAC berlapis

Akses cluster masih tunggal pemilik, sehingga sistem peran multi-pengguna sengaja tidak dibangun. Perlindungannya bertumpu pada izin berkas dan cadangan terenkripsi.

Cara membaca daftar ini: semua yang di bawah judul “masih terbuka” adalah keputusan yang diambil sadar pada skala sekarang, bukan hal yang luput. Daftar ini ditulis justru agar tidak hilang dari radar ketika cluster tumbuh.

12Glosarium

Istilah yang muncul di dokumen ini, dijelaskan tanpa jargon.

Cluster
Kumpulan mesin yang bekerja sebagai satu komputer besar. Di sini isinya dua mesin.
Control plane
Bagian yang mengatur: menerima perintah, memutuskan pod ditaruh di mana, dan menyimpan keadaan cluster. Analogi: kantor mandor.
Node
Satu mesin anggota cluster. Master mengatur, worker menjalankan aplikasi.
Pod
Satuan terkecil yang dijalankan Kubernetes, biasanya berisi satu container aplikasi.
Namespace
Sekat di dalam satu cluster. Dua namespace tidak bisa saling menimpa meski nama resource-nya sama.
Deployment
Aturan yang menjaga jumlah salinan sebuah aplikasi tetap sesuai keinginan.
StatefulSet
Seperti Deployment, tetapi untuk aplikasi yang butuh identitas dan penyimpanan tetap, misalnya database.
Service
Alamat tetap di dalam cluster untuk menjangkau sekumpulan pod yang alamatnya berubah-ubah.
Ingress / IngressRoute
Aturan yang memetakan nama domain dari luar ke Service di dalam. IngressRoute adalah bentuk khas Traefik.
hostPort
Cara membuat pod mendengarkan langsung di port milik mesin, dipakai karena VPS tidak punya penyeimbang beban dari penyedia.
Secret
Tempat menyimpan password dan token di dalam cluster, terpisah per namespace dan tidak ikut masuk repositori kode.
ConfigMap
Sama seperti Secret, tetapi untuk nilai yang tidak rahasia.
PV / PVC
Ruang penyimpanan tetap dan permintaan atasnya, supaya data tidak hilang saat pod dimulai ulang.
StorageClass
Aturan yang menentukan bagaimana ruang penyimpanan baru dibuat otomatis ketika diminta.
CNI / Calico
Lapisan jaringan di dalam cluster yang memberi setiap pod alamat sendiri dan menegakkan aturan siapa boleh menghubungi siapa.
NetworkPolicy
Aturan lalu lintas antar pod. Tanpa CNI yang mendukungnya, aturan ini diterima tetapi tidak berlaku.
WireGuard
Terowongan terenkripsi antar mesin, dipakai karena penyedia tidak menyediakan jaringan privat.
containerd
Mesin yang benar-benar menjalankan container di setiap node. Kubernetes hanya yang mengatur.
kubeadm
Alat untuk menyalakan cluster pertama kali dan menggabungkan node baru ke dalamnya.
kubectl
Perkakas baris perintah untuk berbicara dengan cluster. Di sini hanya terpasang di node master.
Helm
Pemasang paket siap pakai untuk Kubernetes. Di sini hanya dipakai untuk Traefik.
Kustomize
Cara menyusun manifest berlapis: satu dasar bersama, lalu penimpaan kecil per environment.
Image / Registry / GHCR
Paket aplikasi siap jalan, gudang tempat menyimpannya, dan gudang milik GitHub yang dipakai di sini.
CI / CD
Menguji dan mengemas otomatis, lalu memasang ke server. Di sini yang otomatis hanya bagian pertama.
ArgoCD
Alat pemasangan otomatis yang hidup di dalam cluster dan menarik dari repositori, bukan didorong dari luar. Belum dipasang.
SPA
Aplikasi web yang seluruh halamannya berupa berkas statis, dan memanggil API dari peramban pengguna.
SeaweedFS
Penyimpanan berkas yang dijalankan sendiri di dalam cluster.
UFW
Penyaring koneksi di tingkat sistem operasi, bekerja sebelum permintaan sampai ke pod.

13Catatan sumber

Dari mana isi dokumen ini berasal, dan apa yang belum terverifikasi.

Sumber kebenaran

  • Rangkuman setup cluster yang mencatat hanya langkah dengan keluaran nyata, ditulis 28 Agustus 2026 dan dikoreksi 11 September 2026.
  • Panduan penyebaran langkah demi langkah untuk repositori swt-kmtxpumit-platform-fs, versi 11 September 2026.
  • Dokumentasi versi lengkap di deploy/k8s/README.md dan riwayat audit di dalam repositori.
  • Keluaran perintah pemeriksaan di kedua node, antara lain status tunnel, daftar node, daftar pod, dan status firewall.

Belum terverifikasi

  • Rincian aturan firewall untuk port 80 dan 443 di panel penyedia, yaitu sumber yang diizinkan dan apakah dipasang di kedua node.
  • Keluaran terbaru status UFW di kedua node. Keluaran yang tercatat berasal dari 28 Agustus dan sudah tidak lengkap.
  • Apakah perintah pembuatan admin pertama benar-benar bisa dikompilasi dan dijalankan terhadap database sungguhan.
  • Apakah ResourceQuota dan LimitRange per namespace pernah benar-benar terpasang.
  • Seluruh isi namespace production, karena namespace itu belum pernah dijalankan sekalipun.

Cara memperbarui dokumen ini: setiap perubahan pada daftar image, nama domain, aturan firewall, atau struktur overlay perlu tercermin di sini. Ubah juga tanggal verifikasi di bagian atas agar pembaca tahu seberapa baru isinya. Bila sebuah angka atau aturan belum dilihat sendiri, tulis di bagian “belum terverifikasi” dan jangan dikutip sebagai final.
